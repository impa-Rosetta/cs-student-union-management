# 学生联盟统一工作管理平台完善设计

日期：2026-11-05  
状态：已完成分节确认，待最终审阅

## 1. 背景与目标

当前系统已经具备活动管理、主任务与干事子任务、部门办事中心、通知、附件、审核留痕、教师监管等功能，但不同模块在数据结构、状态名称、负责人关联、待办生成和进度统计方面各自实现，逐渐形成多套并行规则。

本轮完善以“活动全过程管理”为主线，同时保留各部门独立日常业务。目标不是重写所有既有模块，而是在现有业务之上建立统一工作管理层，使同一件工作能够被个人、部门、活动、主席团和教师从各自视角查看，且只有一个真实业务来源。

核心业务主线：

`活动 → 里程碑 → 部门主任务 → 干事子任务 → 部门服务申请 → 成果与审核 → 归档`

系统同时支持不属于活动的日常事项，例如白卡制作、例会通报和组织变动。

## 2. 参考模型与设计原则

本设计综合采用以下成熟项目管理做法：

- Jira Service Management 将用户看到的“申请”和内部人员处理的“工作项”视为同一工作的不同视角，并通过队列组织待办。
- Microsoft Project Operations 使用 WBS 将项目拆分为汇总任务和最底层执行任务，并从执行任务向上汇总计划与进度。
- Asana Portfolio 以项目组合方式展示项目状态、风险、逾期、负责人和工作负荷。
- GitHub Projects 通过统一字段、时间线和图表从同一批工作项生成不同管理视图。
- Jira 审计日志记录关键配置、权限和业务变更的操作者与时间。

设计原则：

1. 原业务表是业务数据唯一来源，统一工作项不能复制完整表单。
2. 同一工作只能有一个进度来源，禁止为了展示重复生成任务。
3. 活动关联由业务类型决定，不做一刀切。
4. 部门保留业务化状态，管理视图使用统一状态分组。
5. 所有统计从真实执行记录计算，不再依赖手工总体进度。
6. 教师只读监管，业务角色按职责执行操作。
7. 先保证数据、权限和状态一致，再增加高级展示。

## 3. 总体架构

系统分为四层：

### 3.1 业务域层

保留现有活动、任务、教室借用、采购、例会通报、组织管理、白卡制作等业务模块。每个模块继续拥有自己的表单字段、专属状态机、附件和审核规则。

### 3.2 统一工作管理层

新增统一工作项索引、统一状态映射、负责人和部门关联、期限与风险计算、待办队列、活动关联和统一事件索引。

该层不替代业务域，而是为所有管理视图提供一致的数据口径。

### 3.3 视图与监管层

包括“我的工作”、活动中心、部门工作台、主席团协调中心和教师监管中心。不同视图查询同一批工作项，只按照用户权限、工作关系和展示目的进行筛选与聚合。

### 3.4 基础能力层

包括账号与组织、权限、通知、附件、审计、事务、数据迁移和系统配置。

## 4. 统一工作项模型

新增 `work_items` 索引。建议字段如下：

| 字段 | 说明 |
| --- | --- |
| id | 工作项稳定编号 |
| source_type | 来源类型，如 task、subtask、venue_request、purchase_request、white_card |
| source_id | 原业务记录编号 |
| title | 用于列表和监管展示的标题 |
| status_group | 统一状态分组 |
| native_status | 原业务状态快照，便于查询与排错 |
| activity_id | 可选活动编号 |
| owner_department_id | 负责部门稳定编号 |
| assignee_account_id | 当前执行人账号编号，可为空 |
| requester_account_id | 发起人账号编号 |
| priority | 优先级 |
| planned_start_at | 计划开始时间 |
| due_at | 截止时间 |
| completed_at | 实际完成时间 |
| blocked | 是否阻塞 |
| blocked_reason | 当前阻塞原因 |
| next_actor_type | 下一处理主体类型 |
| next_actor_id | 下一处理主体编号 |
| updated_at | 最近更新时间 |

`source_type + source_id` 必须唯一，保证一个原业务记录只生成一个统一工作项。

工作项只保存列表、筛选、监管和待办所需的公共字段。完整申请内容、专属字段、附件和审批意见仍从来源业务记录读取。

## 5. 活动关联规则

| 业务类型 | 活动关联规则 | 是否进入活动进度 |
| --- | --- | --- |
| 白卡制作 | 禁止关联活动 | 否 |
| 教室借用 | 选填 | 关联时进入 |
| 采购、报销等服务 | 选填 | 关联时进入 |
| 活动主任务与子任务 | 默认关联，允许主席团创建独立临时任务 | 关联时进入 |
| 例会通报、组织管理 | 默认不关联 | 否 |

从活动页面发起教室借用时，系统自动带入活动名称、使用时间、地点需求和参与部门，但这些字段允许发起人检查和补充。

教室借用也必须能从公共入口独立发起，不要求必须存在活动。

## 6. 统一状态模型

不同业务保留原有状态，并映射为以下管理状态：

| 统一状态 | 含义 |
| --- | --- |
| 待处理 | 已创建，尚未开始处理 |
| 进行中 | 当前有人执行 |
| 等待他人 | 等待其他部门、申请人或外部系统结果 |
| 待审核 | 已提交成果，等待具有审核权限的人员处理 |
| 已完成 | 工作已经闭环 |
| 已取消 | 工作被撤销或终止 |

每个工作项必须同时计算“当前等待谁处理”。界面显示业务化流程，例如：

`科创中心提交 → 等待办公室审核 → 等待办公室外部申请 → 已确认教室 → 完成`

状态映射集中维护，禁止各页面自行判断同一业务状态属于哪一组。

## 7. 活动进度、健康状态与风险

### 7.1 进度口径

- 主任务没有子任务时，主任务作为最底层执行项计入进度。
- 主任务已经拆分子任务时，只计算子任务，避免父子重复。
- 关联活动的部门服务申请作为独立执行项计入进度。
- 不关联活动的日常工作不影响活动进度。
- 已完成计 100%，进行中计 50%，其余未完成状态计 0%。
- 活动总体进度由最底层执行项平均汇总，首版不引入复杂权重。

活动页面取消手工修改总体进度，保留负责人填写的进展说明、当前风险和下一步计划。

### 7.2 健康状态

系统自动计算：

- 正常：无逾期、无阻塞，关键事项按计划推进。
- 关注：存在临近截止、长期未更新或等待审核时间较长的事项。
- 有风险：存在逾期、阻塞或关键里程碑无法按期完成的事项。

健康状态由系统事实计算，负责人可以补充说明，但不能直接覆盖事实标记。

## 8. 角色与权限

### 8.1 教师

- 查看全部活动、任务、部门申请、附件、时间轴和审计记录。
- 支持按活动、部门、人员、状态和时间筛选。
- 只读，不执行任何业务操作。

### 8.2 主席团

- 创建和管理活动。
- 分配部门主任务，协调跨部门事项。
- 查看全部协作进度、逾期、阻塞、无负责人事项和部门负荷。
- 可执行重新指派、调整期限等协调操作，但必须留痕。

### 8.3 部门负责人

- 查看本部门全部工作项。
- 领取或分派部门事项，拆分为干事子任务。
- 审核本部门干事成果。
- 查看本部门参加的活动和关联服务。

### 8.4 干事

- 查看本人负责的工作项。
- 开始、提交、补充说明和上传成果。
- 标记阻塞并说明所需协助。

### 8.5 部门业务处理人

按所在部门和业务状态处理教室、采购、白卡等专属流程。权限不能仅依赖前端隐藏按钮，服务端必须校验角色、部门、负责人和当前状态。

### 8.6 管理员

管理账号、组织结构、业务模板和系统配置。管理员不默认代替业务人员完成业务审核。

## 9. 页面信息架构

### 9.1 我的工作

作为所有业务角色的统一首页，包含：

- 等待我处理
- 我发起的
- 我负责的
- 即将到期
- 已逾期
- 被退回或被阻塞
- 最近完成

普通任务和部门申请使用统一卡片骨架，并清楚标明业务类型、来源部门、活动关系和下一处理人。

### 9.2 活动中心

每个活动包含：活动概况、里程碑、任务分解、部门服务、时间轴、文件成果、风险与问题、操作记录。

活动时间轴同时展示主任务、子任务以及与该活动关联的教室、采购等服务事项，但不会展示白卡等日常业务。

### 9.3 部门工作台

保留办公室、生活部、组织部、学习部等专属功能，并统一增加：部门待办、本周到期、逾期事项、等待其他部门、本部门活动、最近完成成果。

### 9.4 主席团协调中心

展示所有进行中活动、部门完成率、逾期与阻塞、无负责人事项、工作量异常、长时间等待审核事项、活动风险和下一里程碑。

### 9.5 教师监管中心

在现有只读 WBS/时间轴基础上增加活动健康状态、关联部门服务、延期原因、最终成果和统一筛选。

### 9.6 统一详情结构

所有工作项详情统一包含：基本信息、当前状态、负责人、处理流程、附件成果、历史记录。业务差异仅体现在表单字段和允许执行的操作。

## 10. 项目管理能力

### 10.1 任务依赖

首版支持最常用的“完成后开始”依赖。若前置工作未完成，后续任务可查看但不能标记开始。依赖变更必须记录审计事件。

### 10.2 阻塞管理

执行人可以标记阻塞，必须填写原因和希望谁协助。解除阻塞必须填写处理结果。阻塞事项进入部门负责人和主席团协调队列。

### 10.3 重新指派与延期

具有权限的负责人可以重新指派执行人或修改期限。操作必须记录原值、新值和原因，并向新旧负责人发送站内通知。

### 10.4 活动模板

可将成熟活动的任务结构保存为模板。模板复制任务层级、任务类型、相对时间和部门角色，不复制历史人员、实际日期、附件、状态和审核记录。

### 10.5 提醒

临近截止、已经逾期、等待审核、被退回和阻塞时生成站内提醒。当前阶段不接入外部消息平台。

## 11. 审计、事务与数据一致性

统一业务事件至少记录：业务类型、业务编号、活动编号、操作者账号、操作者角色、操作名称、原状态、新状态、关键字段变更、说明和时间。

涉及原业务记录、统一工作项、通知和审计的操作必须处于同一个数据库事务。任何一步失败时整体回滚，避免出现状态已变但待办或通知未更新。

读取权限也必须在服务端执行。公共状态接口不能再向所有已登录用户返回完整任务、活动和通知数据。

历史数据通过幂等迁移补建工作项索引。迁移可重复运行，不能删除或覆盖原业务记录。

## 12. 异常处理

- 来源业务记录不存在：工作项标记为数据异常，不在普通列表中静默丢失。
- 负责人账号停用：工作项进入“无有效负责人”协调队列。
- 部门或人员调整：历史事件保留原显示名称，新工作项使用稳定编号关联当前组织。
- 活动删除或归档：已有关联工作不得直接物理删除；归档活动保持只读查询。
- 状态映射缺失：接口返回明确错误并记录系统审计，不能默认视为已完成。
- 事务冲突：返回可重试提示，不使用前端旧数据覆盖服务端新状态。

## 13. 测试与验收

至少覆盖：

1. 一个业务记录只能生成一个工作项。
2. 白卡不能关联活动。
3. 教室申请可以独立发起，也可以关联活动。
4. 有子任务的主任务不会被重复计入活动进度。
5. 不同业务状态正确映射到统一状态。
6. 待办只发送给当前应处理的人或部门。
7. 普通成员无法读取无关部门的受限数据。
8. 教师可读取全部监管数据但无法修改。
9. 修改负责人、期限和阻塞状态生成完整审计。
10. 事务任一步失败时业务、工作项、通知和审计均不产生部分更新。
11. 历史数据迁移可重复执行且结果不重复。
12. 现有办公室、生活部、组织部、学习部和教师监管回归测试通过。

## 14. 分批实施

### 第一批：数据与权限治理

- 统一账号、部门和负责人稳定编号。
- 收紧公共接口数据范围。
- 建立统一状态映射。
- 改为真实执行项计算活动进度。
- 为后续工作项层准备迁移和事务基础设施。

### 第二批：统一工作项与“我的工作”

- 建立工作项索引和统一事件索引。
- 接入任务、子任务、教室申请、采购和白卡。
- 建立个人与部门待办队列。
- 完成历史记录补建。

### 第三批：活动全过程完善

- 将可关联的部门服务纳入活动时间轴。
- 增加依赖、阻塞、重新指派和延期原因。
- 增加活动模板和自动健康状态。

### 第四批：工作台整合与工程治理

- 完善主席团、部门和教师管理视图。
- 统一工作项详情交互。
- 拆分过大的前端文件和重复业务判断。
- 补齐迁移、事务、回归测试和部署检查。

## 15. 明确不在本轮范围内的事项

- 不接入微信公众号、企业微信、钉钉等外部平台。
- 不把白卡纳入活动管理。
- 不重写所有部门专属状态机为通用流程引擎。
- 不实现复杂工时、成本核算或挣值管理。
- 不改变教师只读定位。
- 不删除现有业务数据或历史附件。
