# 组织部办事中心设计规格

日期：2026-10-28  
状态：设计已确认，待实现  
适用项目：计算学院学生联盟管理系统

## 1. 背景与目标

当前系统已经有“组织与成员”模块，负责维护正式的部门、成员和角色档案；“部门办事中心”则用于承载各部门的日常业务流程。组织部办事中心不能另建一套相互独立的成员名册，而应围绕成员加入、调动、任职、离任、考核和组织事务形成可审批、可追踪、可归档的工作流，并在审批完成后同步正式成员档案。

本期目标如下：

1. 实现学生联盟成员全生命周期的线上办理。
2. 实现月度或学期考核的建立、填写、确认和归档。
3. 对团务、推优等依赖校级平台的事项进行进度、材料和结果跟踪，不重复建设正式校级系统。
4. 保留申请、审核、退回、驳回、生效和归档的完整操作记录。
5. 将组织部入口接入“部门办事中心”，保持与办公室、生活部一致的使用方式。

## 2. 范围

### 2.1 本期实现

- 成员入部申请。
- 跨部门调动申请。
- 职务调整申请。
- 离任与交接申请。
- 组织部审核及主席团最终确认。
- 审批通过后同步正式成员档案。
- 月度、学期或专项考核。
- 成员考核评分、评语和结果确认。
- 团务、推优等外部组织事务的办理跟踪。
- 附件、审批意见、状态历史和操作日志。
- 组织部工作台统计和待办提醒。

### 2.2 本期不实现

- 代替学校团委、教务或统一身份平台完成正式团务操作。
- 复杂的人力资源薪酬、奖惩或学籍管理。
- 自动决定推优、任免或考核结论。
- 删除或覆盖既有“组织与成员”正式档案模块。

## 3. 用户与权限

### 3.1 普通成员

- 新建并维护本人尚未提交的异动申请。
- 提交入部、调动、职务调整或离任申请。
- 查看本人申请进度、审批意见和考核结果。
- 对被退回申请补充材料后重新提交。

### 3.2 组织部成员

- 查看组织部全部待办和历史记录。
- 审核成员异动申请，填写审核意见并通过、退回或驳回。
- 创建考核周期，选择参与成员，录入或汇总考核信息。
- 创建和维护组织事务，上传材料并记录外部平台办理结果。

组织部身份以正式成员档案中的部门归属为准；组织部部长和副部长拥有组织部业务管理权限，普通组织部成员拥有经授权的办理权限。

### 3.3 主席团与系统管理员

- 对组织部审核通过的异动申请作最终确认、退回或驳回。
- 确认考核结果并归档。
- 查看全部组织部业务数据和审计记录。
- 管理异常数据，但不得绕过审计日志静默修改已生效事项。

## 4. 信息架构与界面

从“部门办事中心”选择“组织部”后进入组织部工作台，页面包含四个主区域。

### 4.1 工作概览

- 待组织部审核数量。
- 待主席团确认数量。
- 本学期已生效异动数量。
- 进行中的考核周期数量。
- 临近截止或逾期的组织事务数量。
- 最近办理记录和当前用户待办。

### 4.2 成员异动

列表支持按类型、状态、申请人、目标部门和时间筛选。详情展示申请前信息、拟变更信息、申请原因、交接说明、附件、审批意见和完整时间线。

申请表根据异动类型动态显示字段：

- 入部：姓名、学号、联系方式、目标部门、拟任职务、申请理由、附件。
- 调动：当前部门、目标部门、当前职务、拟任职务、调动原因、交接内容。
- 职务调整：当前职务、拟任职务、生效日期、调整原因。
- 离任：离任日期、离任原因、交接对象、交接清单、附件。

### 4.3 考核管理

考核周期包含名称、类型、起止日期、适用范围、评分说明和负责人。考核记录包含成员、分数、等级、评语、改进建议和确认状态。

第一版采用人工录入或汇总，避免在缺乏明确制度时固化复杂自动评分规则。

### 4.4 组织事务

用于跟踪团务、推优及其他依赖外部平台的事项。每项事务包括类别、标题、负责人、参与成员、截止时间、所需材料、外部平台、当前进度、办理结果和附件。系统只记录过程与结果，不宣称已在外部平台完成正式业务。

## 5. 业务流程

### 5.1 成员异动状态机

主流程：

`草稿 → 待组织部审核 → 待主席团确认 → 已生效`

分支流程：

- 待组织部审核可退回为“待申请人修改”或结束为“已驳回”。
- 待主席团确认可退回为“待组织部复核”或结束为“已驳回”。
- 待申请人修改可重新提交至“待组织部审核”。
- 待组织部复核可重新提交至“待主席团确认”。
- 已生效记录不可直接编辑；后续变化必须新建异动申请。

最终确认使用数据库事务完成以下操作：

1. 校验申请仍处于待确认状态。
2. 校验目标成员、部门和职务合法。
3. 按异动类型新增或更新正式成员档案。
4. 写入异动事件和通用工作流事件。
5. 将申请标记为已生效并记录生效时间。
6. 创建通知。

需要使用幂等校验，防止重复点击造成重复成员或重复更新。

### 5.2 考核状态机

`草稿 → 进行中 → 待确认 → 已归档`

- 草稿可维护范围和评分说明。
- 进行中可录入和修改考核记录。
- 待确认只允许主席团或管理员确认、退回。
- 已归档只读；修正必须留下补正记录。

### 5.3 组织事务状态机

`草稿 → 办理中 → 待结果确认 → 已完成 → 已归档`

办理中可标记受阻、补充材料和延期。完成时必须填写结果说明；涉及外部平台时可记录外部流水号或结果文件，但不把本系统状态等同于外部平台的法定状态。

## 6. 数据设计

### 6.1 成员异动申请

建议新增 `organization_change_requests` 表，核心字段包括：

- 主键、申请编号、异动类型、状态。
- 申请人用户标识、关联成员标识。
- 当前部门和职务、目标部门和职务。
- 生效或离任日期、申请原因、交接说明。
- 当前处理人、组织部审核意见、主席团确认意见。
- 创建、提交、生效和更新时间。
- 用于幂等同步的正式档案同步标识。

建议新增 `organization_change_events` 表保存每次状态变化、操作者、意见和时间。

附件继续复用现有文件上传能力，并通过业务类型和业务主键关联，不在新表中保存文件二进制数据。

### 6.2 考核

- `organization_assessment_cycles`：周期名称、类型、范围、说明、状态、负责人、起止日期。
- `organization_assessment_records`：周期、成员、分数、等级、评语、改进建议、录入人、确认状态。

周期与成员记录使用唯一约束，防止同一成员在同一周期重复产生两条主记录。

### 6.3 组织事务

建议新增 `organization_affairs` 表，保存类别、标题、负责人、参与人、外部平台、截止时间、状态、材料说明、结果说明和归档时间。

### 6.4 与正式档案的关系

现有成员表是人员与部门归属的唯一正式数据源。异动申请在生效前不得改变正式档案；生效后由服务端事务同步正式档案。页面展示成员当前信息时优先读取正式档案，申请表仅保存申请时快照和拟变更内容。

## 7. API 与服务边界

新增组织部专用 API，路径建议为 `/api/organization-department`，按照 `resource` 和 `action` 区分异动、考核和组织事务操作。服务端必须完成权限校验、状态转换校验、字段校验和审计记录，前端禁用按钮不能作为权限保障。

读取接口返回：

- 当前用户身份与可执行权限。
- 工作台统计。
- 异动申请及事件。
- 考核周期及记录。
- 组织事务。
- 创建表单所需的正式部门、职务和成员选项。

写接口采用明确动作，例如 `submit-change`、`organization-review`、`presidium-confirm`、`start-assessment`、`archive-assessment` 和 `complete-affair`，避免由客户端任意指定下一状态。

## 8. 校验、异常与安全

- 学号、部门、职务和日期必须通过服务端校验。
- 调动目标不能与当前部门完全相同。
- 离任必须填写交接说明或明确标记“无交接事项”。
- 非组织部人员不得执行组织部审核。
- 非主席团或管理员不得确认生效和归档考核。
- 状态已经变化时返回冲突提示，要求刷新后重试。
- 正式档案同步失败时整个确认事务回滚，申请保持待确认状态。
- 所有拒绝、退回和补正动作必须填写意见。
- 列表默认最小化展示敏感个人信息，详情访问受权限控制。

## 9. 通知与审计

在提交、退回、驳回、待最终确认、生效、考核待确认、事务逾期等节点复用现有通知能力。所有状态变化写入业务事件表，同时写入项目已有的通用工作流事件，以支持统一时间线和验收追踪。

通知失败不应回滚已经成功的核心业务事务，但应记录可重试错误；正式档案同步失败必须回滚。

## 10. 测试与验收

### 10.1 自动化测试

- 各状态机合法和非法转换测试。
- 普通成员、组织部、主席团和管理员权限测试。
- 四类成员异动同步正式档案测试。
- 重复确认的幂等测试。
- 同步失败事务回滚测试。
- 考核周期和成员唯一约束测试。
- 组织事务办理与归档测试。
- API 集成测试和现有回归测试。

### 10.2 人工验收主路径

1. 普通成员创建并提交跨部门调动申请。
2. 组织部退回，申请人补充交接材料后重新提交。
3. 组织部通过，主席团最终确认。
4. 申请变为已生效，正式成员档案部门随之更新，时间线完整。
5. 组织部创建学期考核、录入结果、提交确认并归档。
6. 组织部创建推优事务，记录外部办理进度和结果后归档。

## 11. 兼容性与迁移

新增数据表使用独立迁移，不改写既有业务表。正式成员档案同步复用当前组织管理服务。部门办事中心仅增加“组织部”专属工作区分支，其他部门入口及办公室、生活部现有功能保持不变。

数据库迁移和首次读取应兼容本地 SQLite 开发环境，并保持项目已有 PostgreSQL 结构定义的一致性。迁移失败时不得静默忽略。

## 12. 实现顺序

1. 定义状态机、数据库结构和迁移。
2. 实现权限判断与组织部 API。
3. 实现成员异动及正式档案事务同步。
4. 实现考核管理。
5. 实现组织事务跟踪。
6. 实现组织部工作台并接入部门办事中心。
7. 补充自动化测试、人工验收清单和需求文档映射。

## 13. 已确认的设计决策

- 组织部办事中心采用“成员全生命周期管理”方案。
- 正式成员档案只保留一套，由现有“组织与成员”模块负责展示和维护。
- 异动采用组织部审核、主席团确认的两级审批。
- 团务和推优只做过程与结果跟踪，不替代学校正式平台。
- 第一版考核以人工录入和确认流程为主，不预设复杂自动计分制度。
