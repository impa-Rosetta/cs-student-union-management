# 申请补充与材料管理设计

## 1. 目标

补齐办公室申请和生活部采购申请在“草稿填写、退回补充、材料上传、重新提交”环节的 P0 能力。申请人在可编辑状态下应能修改业务字段和附件；进入审核或后续办理阶段后，申请内容保持只读，避免审批依据被静默改变。

本轮对应需求为 `SRS-OFF-002`、`SRS-OFF-004`、`SRS-OFF-005`、`SRS-LP-001`、`SRS-LP-002` 和 `SRS-LP-003`。

## 2. 方案选择

采用“共用编辑规则，保留领域接口”的方案：办公室申请和采购申请各自保留现有 API、存储和页面，但共享同一组交互原则与附件规则。这样可以在不引入新的通用表单框架的情况下完成闭环，同时避免两个领域被一个复杂抽象强行耦合。

未采用的方案：

- 新建通用申请引擎。扩展性较强，但会重构现有状态机、数据表和界面，不适合当前课程项目阶段。
- 仅在前端允许修改。实现较快，但无法防止绕过页面修改审核中的申请，不符合服务端权限要求。

## 3. 范围

本轮实现：

- 办公室申请在“草稿”和“待补充材料”状态下编辑。
- 办公室申请维护材料清单，上传、查看和移除附件。
- 采购申请在“草稿”和“待补充材料”状态下编辑。
- 采购明细新增、修改、删除，支持商品链接、商品图片和备注。
- 采购申请上传、查看和移除通用附件。
- 修改操作的服务端权限、状态校验、专属事件和统一审计记录。
- 修改失败后保留当前表单内容，成功后刷新列表和详情。
- API、状态约束和关键界面的自动化测试。

本轮不实现：

- 自动识别发票、商品链接或图片内容。
- 附件在线编辑、版本管理或批量压缩下载。
- 审核人员直接改写申请人的原始内容。
- 已完成申请的内容修改；如需继续处理，应通过既有重新打开流程回到允许的业务状态。

## 4. 统一编辑规则

### 4.1 可编辑状态

- 办公室申请：`草稿`、`待补充材料`。
- 采购申请：`草稿`、`待补充材料`。
- 只有 `requesterUsername` 与当前账号一致的申请人可以编辑。
- 管理员、主席和经办人不能代替申请人改写原始申请；他们通过退回原因指导补充。
- 任何其他状态下的编辑请求均返回 `409`，越权编辑返回 `403`，记录不存在返回 `404`。

### 4.2 保存与提交

保存修改不会改变当前状态。申请人可以先多次保存，再执行现有 `submit` 操作。每次成功保存均更新时间并产生 `update` 事件；重新提交仍由现有状态机记录 `submit` 事件。

前端在保存期间禁用重复提交。服务端写入失败时返回中文错误，页面保留用户尚未成功保存的表单和附件选择。

### 4.3 字段校验

办公室申请：

- 标题必填。
- 场地申请的开始和结束时间同时填写时，结束时间不得早于开始时间；预计人数必须为正数。
- 报销金额填写后必须大于零。
- 材料项由固定模板初始化，申请人只能修改完成状态，不能伪造材料键或删除必需项。

采购申请：

- 标题和用途必填，至少保留一项有效物品。
- 每项物品必须填写名称，数量必须为正整数，预算单价不得为负数。
- 每项物品至少提供商品链接或商品图片之一。
- 预算总额由服务端根据数量和预算单价重新计算，不接受客户端直接指定总额。

## 5. API 设计

### 5.1 办公室申请

继续使用 `PATCH /api/office-requests`。当请求包含 `action: "update"` 时，读取 `data` 中允许修改的字段：

- `title`、`activityId`、`activityName`、`deadline`、`description`
- `details`、`materials`、`attachments`

服务端先读取原申请，再依次执行归属校验、状态校验、字段校验和附件结构校验。写入成功后追加 `office_request_events.update`，并写入 `workflow_events`，前后状态相同。

### 5.2 采购申请

继续使用 `PATCH /api/life-department`。请求使用：

- `kind: "purchase"`
- `action: "update"`
- `id`
- `data`：标题、活动、用途、期望时间、收款人、明细和附件

存储层新增完整更新采购基础字段、附件和明细的函数。明细更新在一个逻辑写入过程中先校验全部数据，再替换当前申请的明细记录。预算总额由服务端计算。成功后追加 `purchase_events.update` 和统一审计事件。

### 5.3 附件

附件仍通过现有 `/api/files` 上传、下载和删除。业务保存只写入已成功上传的附件元数据。移除附件时，页面先从申请草稿中移除；业务保存成功后不再引用该对象。为避免误删其他业务仍在使用的对象，本轮不自动删除对象存储中的文件，后续可通过未引用附件清理任务处理。

## 6. 存储设计

办公室申请已经使用 `details_json`、`materials_json` 和 `attachments_json`，不新增数据表。

采购申请沿用现有 `purchase_requests`、`purchase_items` 和 `purchase_events`：

- 扩展 `updatePurchase`，允许更新标题、活动、用途、期望时间、预算总额、收款人和附件。
- 新增替换采购明细的存储操作，确保写入前完成全量校验。
- 商品图片继续使用 `purchase_items.image_url` 保存对象存储下载地址或附件键；界面只接受系统上传结果，不接受任意脚本内容。

本轮不需要数据库迁移。

## 7. 界面设计

### 7.1 办公室

在详情弹窗中，当当前用户是申请人且状态可编辑时显示“编辑申请”。编辑弹窗复用新建申请字段，并增加：

- 材料清单复选项。
- 多附件上传区、文件列表、查看和移除操作。
- “保存修改”和“保存并提交”两个动作。

详情页继续展示当前材料完成情况和附件。审核中及结束状态不显示编辑入口。

### 7.2 采购

在采购详情中，当当前用户是申请人且状态可编辑时显示“编辑申请”。编辑界面支持：

- 增加和删除采购明细。
- 物品名称、数量、预算单价、商品链接和备注。
- 为每项物品上传一张商品图片，支持替换和移除。
- 通用附件上传、查看和移除。
- 实时显示预算合计，但最终金额以服务端计算为准。
- “保存修改”和“保存并提交”两个动作。

删除最后一项采购明细时保留一个空白行，避免表单进入不可操作状态。

## 8. 权限与安全

- 前端按钮隐藏只用于改善体验，所有归属和状态规则在 API 中重新校验。
- 更新请求采用字段白名单，忽略或拒绝状态、申请人、经办人、实际金额、办公室关联编号等不可编辑字段。
- 普通申请人不能通过更新接口修改审核结果、状态或其他人的申请。
- 附件响应只使用现有附件结构，不把对象存储凭据返回浏览器。
- 修改动作写入统一审计，至少包含实体、动作、当前状态、操作人和时间。

## 9. 错误处理

- 表单校验失败返回 `400` 和具体字段原因。
- 申请人不匹配返回 `403`。
- 状态已被他人推进返回 `409`，页面提示刷新后重试。
- 附件上传失败仅标记该文件失败，不清空其余字段和已上传附件。
- 采购明细保存失败时不应留下部分替换结果；若当前数据库适配层无法提供跨语句事务，则先完成全量校验，并将替换操作封装在单一存储函数中，同时用集成测试验证失败路径不改变原数据。

## 10. 测试与验收

自动化测试至少覆盖：

1. 申请人修改草稿办公室申请并保存材料和附件。
2. 退回后的办公室申请补充材料并重新提交。
3. 他人不能修改申请，审核中和已完成申请不能修改。
4. 采购申请修改多项明细，服务端重新计算预算总额。
5. 采购明细缺少商品链接和图片时拒绝保存。
6. 采购附件和商品图片跨刷新保留。
7. 采购被退回后可以修改并重新提交。
8. 更新动作写入领域事件和统一审计。
9. 页面仅在正确角色和状态下显示编辑入口。
10. 完整构建、类型检查及现有测试套件继续通过。

人工验收路径：普通成员创建办公室场地申请并保存草稿，补充材料和附件后提交；办公室退回后，申请人再次编辑并提交。随后创建一份包含两个物品的采购申请，为物品提供链接或图片，生活部退回后补充附件并重新提交。两条流程刷新页面后字段、附件、状态和处理轨迹均保持一致。
